## 〔0:40–1:30〕二、前后端打通 + Agent/RAG 接入

原来后端有个严重问题：**前端实际连的是另一套 Express 服务**，我们写的 FastAPI 完全没被用到。而且 FastAPI 里的核心方法全是 TODO，出题是写死的 5 条问题，评估永远返回 75 分。

我做的改动是：
- **统一 API 契约** —— 让 `start` 接口一次性生成 3 道题返回给前端，提交答案时带上 `questionId` 精确定位题目，而不是靠数组下标猜
- **把 stub 接到真实 Agent** —— 出题调面试官 Agent、评估调评估 Agent、追问也动态生成

这里有个关键设计：**try-catch 降级**。真实 Agent 调用失败时，自动回退到占位逻辑。这样配置了 API Key 就走真实大模型，没配或者断网也能照常跑，不会崩。

## 〔1:30–2:50〕三、⭐ LCEL 管道（重点）

这个是我想重点说明的。

考核标准里有一条很明确：**如果只是裸调用大模型接口、没有搭建 LCEL 管道，后端总分上限 22 分**。原来的代码正好踩中这条 —— `agents/base.py` 里就是直接 `llm.invoke()`，没有任何管道。

我做的改造是：

- 在 **Agent 基类**里封装了一个 `_build_chain` 方法，它返回的是标准的 **`prompt | llm | parser`** 三段式管道
- **面试官 Agent** 的出题和追问、**评估 Agent** 的评分，主流程全部改走这个管道
- 评估那里还用了 **`JsonOutputParser`**，模型输出直接被解析成字典，省掉了手写正则提取 JSON 的麻烦

这个管道**不是包装出来的假象**：它返回的对象类型是 LangChain 的 `RunnableSequence`，内部三段分别是 `ChatPromptTemplate`、`ChatOpenAI`、`StrOutputParser`，是可以现场验证的。而且因为它是标准的 Runnable，后续还能用管道操作符继续拼接、做流式输出，扩展性是有的。

## 〔2:50–3:40〕四、工程健壮性 + 代码卫生

第四块是一些让代码更工程化的补齐工作：

- **重试机制**：网络超时、限流、5xx 错误自动指数退避重试，最多 3 次
- **Key 解耦**：本地 RAG 检索的 Agent 不再强制要求 LLM 的 API Key
- **安全配置**：修了 CORS 配置（原来用了 `*` 加 `credentials` 的危险组合）
- **依赖补全**：`requirements.txt` 把缺失的 langgraph、openai 这些都补上了
- **删冗余**：删掉了一个和 agents 功能重复、但从未被调用的 chains 目录

另外配套修了一些 bug，比如追问逻辑判断方向是反的、题库重复、日志路径写死等等。

## 【备答】可能被追问的问题

| 问题 | 一句话回答 |
|------|-----------|
| LCEL 管道在哪？ | `agents/base.py` 的 `_build_chain`，被 interviewer 和 evaluator 的主方法调用 |
| 怎么证明是真管道？ | 返回类型是 `RunnableSequence`，三段式结构可以现场打印验证 |
| 没配 Key 怎么办？ | 自动降级到占位逻辑，整个面试流程仍能跑通 |
| 为什么删 chains 目录？ | 和 agents 功能重复，且从未被路由调用，是死代码 |
| 追问逻辑是什么？ | 分数低于阈值且追问未达上限时触发，由 Agent 动态生成追问内容 |
